Stratégie de copie

Pour une question « risque » : 1) le mécanisme, 2) l'attaque, 3) la conséquence, 4) la mesure. Exemple SUID : « un binaire root s'exécute avec l'EUID 0 ; s'il est vulnérable, un utilisateur obtient root ; d'où la minimisation, l'audit et les capabilities ».

Les QCM sont souvent des définitions du cours. Ne surinterprète pas : la réponse est celle du cours, pas la nuance technique avancée.

1

Architecture des OS & noyaux

Le noyau est le programme qui gère les ressources matérielles et fournit aux applications une interface (appels système). Il s'exécute en mode noyau (privilégié) ; les applications en mode utilisateur.

Type de noyauPrincipeAvantagesInconvénients / exemples
Monolithique non modulaireTout le code (noyau + pilotes) dans un seul bloc binaire.Performant, simple à concevoir.Difficile à maintenir ; une erreur peut tout bloquer. Anciens Unix.
Monolithique modulaireNoyau de base + modules chargeables à chaud.Maintenance, chargement dynamique, performances.Une erreur de module peut déstabiliser le système. Linux.
Micro-noyauNoyau minimal (ordonnanceur, IPC, mémoire) ; services et pilotes en espace utilisateur.Robustesse, isolation, maintenance.Beaucoup d'appels système/IPC, performances moindres. QNX, L4.
HybrideCombine micro-noyau et code monolithique pour les fonctions critiques.Compromis performance/robustesse.Windows (Executive + Kernel), macOS XNU (Mach + BSD).
Exo-noyauNoyau minimal qui protège et multiplexe le matériel ; les abstractions sont dans les applications.Grande flexibilité.Complexité pour les applications.

Linux : noyau monolithique modulaire, chargement à chaud, l'interface graphique ne fait pas partie du noyau. Une distribution = noyau + outils GNU + gestionnaires de paquets + logiciels. Le premier programme lancé en mode utilisateur est systemd (PID 1) sur la plupart des distributions modernes.

QCM

Un noyau est « un programme souvent écrit en C ou en assembleur » et « une partie du code qui s'exécute en mode privilégié ». Il n'inclut pas Bash. Linux est monolithique modulaire ; macOS est hybride (Mach + BSD) ; un micro-noyau contient l'ordonnanceur et l'IPC.

Principes & niveaux de durcissement

Les 4 principes

PrincipeDéfinitionExemple
MinimisationRéduire la complexité et la surface d'attaque au strict nécessaire ; facilite le suivi et la mise à jour.Désinstaller les services inutiles, système minimal, un seul rôle par serveur.
Moindre privilègeChaque entité n'a que les droits strictement nécessaires ; en cas de compromission, les dégâts sont limités (fail securely).Apache lance un processus root puis passe à www-data ; sudo au lieu de root.
Défense en profondeurPlusieurs couches indépendantes et complémentaires ; chaque couche doit être franchie.Auth + chiffrement + firewall + logs + EDR.
Veille & maintenanceSurveiller les vulnérabilités, appliquer les correctifs, journaliser et archiver.Patch management, CERT, logs centralisés.

Le durcissement consiste à vérifier que ces principes sont respectés et à contrôler méthodiquement la conformité par rapport à un référentiel (CIS, ANSSI, STIG, Microsoft Security Baseline). Ce n'est pas un test d'intrusion.

Les 4 niveaux ANSSI

NiveauContexteExemples de mesures
MinimalTout système, systématiquement.Correctifs, limitation des services réseau, PAM robuste, mots de passe complexes.
IntermédiaireServices protégés par plusieurs couches de sécurité.Sudo, journalisation déportée, iptables entrant, partitionnement fin, suppression des setuid inutiles, LDAP.
RenforcéSystèmes exposés à des flux non authentifiés ou de sources nombreuses.iptables local/sortant, auditd, blocage du chargement de modules, suppression des programmes inutiles, chroot, scripts d'audit.
ÉlevéDonnées sensibles accessibles depuis des réseaux non maîtrisés.SELinux RBAC, AppArmor, confinement fort.
Piège

Le niveau dépend de la sensibilité des données et de la robustesse des contrôles d'accès, pas de la difficulté de la mesure. Un serveur exposé publiquement avec des données sensibles = renforcé/élevé.

3

Comptes Linux & fichiers sensibles

/etc/passwd

Lisible par tous. Format : nom:x:UID:GID:GECOS:home:shell. Le x renvoie le mot de passe vers /etc/shadow. Un shell /sbin/nologin ou /bin/false désactive la connexion.

/etc/shadow

Lisible uniquement par root. Contient le hash, la date du dernier changement, les durées min/max, l'avertissement, l'inactivité et l'expiration. C'est là que sont stockés les mots de passe.

Salim:x:1029:1001:Salim Ben:/home/salim:/bin/bash
# champs : login, mdp, UID, GID, commentaire, home, shell

# erreur classique : GID non numérique + shell /bin/passwd invalide

UID, GID et comptes de service

  • UID 0 = root. Un seul compte doit avoir l'UID 0 ; un doublon est une porte dérobée.
  • UID dupliqué = confusion d'identité, contournement des permissions, audit impossible.
  • Chaque service doit avoir son propre compte système, sans shell de connexion, et être désactivé s'il n'est pas utilisé.
  • Le compte nobody partagé par plusieurs services permet à un service de contrôler l'autre (signaux, ptrace, fichiers).
  • Les sessions doivent expirer après inactivité (TMOUT, sshd ClientAliveInterval).
Commandes

id, whoami, getent passwd, awk -F: '{print $1,$3}' /etc/passwd, passwd -l user, usermod -L, chage -l user, lastlog.

4

Permissions & umask

Trois catégories (propriétaire, groupe, autres) et trois droits (lecture r=4, écriture w=2, exécution x=1).

ValeurDroitsUsage
7rwxLecture + écriture + exécution.
6rw-Fichier de données.
5r-xExécutable / répertoire traversable.
4r--Lecture seule.
0---Aucun droit.

Calcul de l'umask

Les droits par défaut sont 666 pour un fichier et 777 pour un répertoire. L'umask retire des droits :

umask 022  → fichier 666 - 022 = 644 (rw-r--r--)
             répertoire 777 - 022 = 755 (rwxr-xr-x)

umask 027  → fichier 666 - 027 = 640 (rw-r-----)
             répertoire 777 - 027 = 750 (rwxr-x---)

umask 002  → fichier 666 - 002 = 664 (rw-rw-r--)
             répertoire 777 - 002 = 775 (rwxrwxr-x)

ANSSI recommande umask 0027. Le umask par défaut est souvent 0022, trop permissif. Pour un répertoire, le droit x permet d'y entrer et de traverser ; pour un fichier, il permet de l'exécuter.

À retenir

Un fichier créé avec umask 002 a les droits 0664 ; avec umask 0027, 0640. Les répertoires accessibles à tous en écriture doivent avoir le sticky bit.

ACL : au-delà du modèle traditionnel, setfacl/getfacl permettent des droits fins par utilisateur. Le modèle traditionnel ne permet pas de retirer un privilège particulier selon le contexte (d'où SELinux/AppArmor).

SUID, SGID, sticky bit

BitValeurEffetExemple
SUID4Le programme s'exécute avec l'EUID du propriétaire, pas celui de l'utilisateur./usr/bin/passwd (root) permet de changer son mot de passe.
SGID2Sur un fichier : s'exécute avec le GID du groupe. Sur un répertoire : les nouveaux fichiers héritent du groupe.Répertoire d'équipe.
Sticky1Dans un répertoire world-writable, seul le propriétaire peut supprimer son fichier./tmp (1777).
chmod 4755 programme    # SUID
chmod 2755 repertoire   # SGID
chmod 1777 /tmp         # sticky
find / -perm -4000 -type f 2>/dev/null   # lister les SUID

Pourquoi le SUID root est dangereux

Un binaire SUID root s'exécute avec EUID 0, même si l'utilisateur est standard. S'il est vulnérable, l'attaquant obtient root. Le risque dépend de la qualité du programme, pas de l'intention.

Surface d'attaqueExemple concretConséquence
Entrées utilisateurBuffer overflow dans un argument, format string.Exécution de code avec EUID 0.
Variables d'environnementPATH, LD_PRELOAD, IFS non nettoyés.Chargement d'une bibliothèque ou commande malveillante.
Race condition / TOCTOUFichier temporaire créé puis remplacé entre la vérification et l'utilisation.Écriture dans un fichier sensible.
Appels système / shellsystem(), popen() avec une entrée non validée.Injection de commande avec privilèges root.
Descripteurs / signauxHéritage de fichiers ouverts, gestion de signaux.Fuite d'informations ou contournement.

Bonnes pratiques

  • Minimiser le nombre de binaires SUID ; auditer régulièrement.
  • N'activer le bit que sur des programmes de confiance, conçus pour cela.
  • Nettoyer l'environnement (PATH, LD_*, IFS), valider les entrées.
  • Abandonner les privilèges dès que possible (setuid/seteuid).
  • Utiliser les capabilities plutôt que root complet (ex. cap_net_bind_service pour bind sur le port 80).
  • Compiler avec les protections mémoire (PIE, canary, RELRO, FORTIFY).
Peut-on supprimer totalement le SUID ?

Non : certains programmes légitimes en ont besoin (passwd, sudo, historiquement ping). On peut le réduire fortement et le remplacer par des capabilities ou des services privilégiés mieux contrôlés.

6

Sudo

sudo permet à un utilisateur d'exécuter une commande avec les privilèges d'un autre compte, selon une politique écrite dans /etc/sudoers et /etc/sudoers.d/. Il permet la traçabilité (logs) et évite le partage du mot de passe root.

Syntaxe

login/group host = (utilisateur cible) commande(s)

salim ALL = (ALL) /bin/date
yann ALL = (ALL) NOPASSWD: /sbin/reboot
%webadmin ALL = (ALL) /etc/init.d/apache2
%wheel ALL = (ALL) ALL, !/bin/su

Les pièges de configuration

ConfigurationProblèmeAttaque
NOPASSWDAucune réauthentification.Quiconque accède au compte exécute la commande.
ALL=(ALL) ALLRoot complet déguisé.Escalade immédiate.
Wildcard /etc/httpd/*Le shell peut développer des chemins.sudoedit /etc/httpd/../shadow → lecture/écriture de /etc/shadow.
Éditeur autorisé (vi, vim)Shell escape depuis l'éditeur.:!sh → shell root.
Script utilisateur autoriséLe script est modifiable par l'utilisateur.L'utilisateur remplace le contenu et obtient root.
Commande avec arguments non fixésArguments arbitraires.systemctl, find -exec, tar --checkpoint-action…

Directives recommandées

  • use_pty : exécuter dans un pseudo-terminal, empêche les processus en arrière-plan de survivre.
  • requiretty : imposer un terminal de login.
  • noexec : interdire l'exécution de commandes depuis sudo (tag NOEXEC).
  • umask=0027 : masque restrictif.
  • ignore_dot : ignorer . dans le PATH.
  • env_reset : réinitialiser l'environnement.
  • passwd_timeout=1 : délai court.
  • logfile="/var/log/sudo.log" : journaliser.
Pseudo-terminal

Un pseudo-terminal (pty) permet d'interagir à distance avec l'entrée/sortie standard, comme SSH. Il est conseillé avec sudo car il isole la session et empêche un programme malveillant de rester en arrière-plan après la commande.

Règle d'or

Ne jamais autoriser un utilisateur à écrire dans un fichier exécuté ensuite par root. sudoedit édite une copie temporaire avec les droits de l'utilisateur, puis applique la modification de façon contrôlée : c'est plus sûr qu'un éditeur lancé en root.

7

PAM, capabilities, MAC

PAM

PAM (Pluggable Authentication Modules) centralise l'authentification et la gestion de session. Les applications appellent PAM ; PAM applique une pile de modules définie dans /etc/pam.d/.

  • auth : vérifier l'identité.
  • account : vérifier que le compte est autorisé (expiration, horaire).
  • password : changer le mot de passe.
  • session : préparer l'environnement (montage, limites).

Modules utiles : pam_unix, pam_pwquality (complexité), pam_faillock (verrouillage), pam_mkhomedir, pam_namespace, pam_tally2. PAM permet donc la centralisation de l'authentification et l'application d'une politique de mot de passe.

Capabilities

Découpent les privilèges root en unités granulaires. Au lieu de donner tout root à un binaire, on lui donne seulement cap_net_bind_service, cap_net_raw, etc.

getcap -r / 2>/dev/null
setcap cap_net_bind_service=+ep /usr/bin/mon_service
capsh --print

SELinux / AppArmor

SELinux

Contrôle d'accès obligatoire (MAC) basé sur des contextes et une politique. Modes : enforcing, permissive, disabled. Commandes : getenforce, sestatus, ls -Z, chcon, restorecon, semanage. Il ajoute une couche au DAC traditionnel.

AppArmor

MAC basé sur des profils par chemin. Plus simple que SELinux. Modes : enforce, complain. Utile pour confiner un service (web, base de données).

Différence DAC / MAC : DAC = le propriétaire décide (modèle Unix). MAC = une politique globale décide, même si le propriétaire autorise. SELinux/AppArmor sont des techniques de cloisonnement et de contrôle d'accès obligatoire.

chroot

chroot change la racine d'un processus. Il faut copier les bibliothèques (ldd), les devices (/dev/null, zero, random) et les fichiers de configuration. Ce n'est pas une frontière de sécurité forte : un root peut s'échapper ; il faut abandonner les privilèges et combiner avec namespaces/SELinux.

8

Durcissement Linux

Partitionnement & montage

  • Séparer /, /boot, /home, /tmp, /var, /var/log pour éviter la saturation et isoler les données.
  • Options de montage : nodev (ignore les devices), nosuid (ignore SUID/SGID), noexec (ignore l'exécution).
  • /tmp avec son propre FS ou tmpfs et noexec : un attaquant ne peut pas y installer de code exécutable.
  • /boot non monté automatiquement, accessible uniquement à root ; System.map protégé (aide à construire des exploits noyau).
  • Chiffrement LUKS pour les données au repos.
  • Mot de passe GRUB pour empêcher la modification des options de démarrage.

Comptes & services

  • Désactiver les comptes inutilisés et les comptes de service (mot de passe invalide, shell nologin).
  • Un compte dédié par service ; pas de nobody partagé.
  • Interdire la connexion root à distance (PermitRootLogin no), utiliser sudo et des clés SSH.
  • Expiration des sessions, bannière, limitation des tentatives.
  • Désactiver les services et paquets inutiles ; réduire la surface d'attaque.

Sysctl : les paramètres à connaître

Appliquer avec sysctl -p ou dans /etc/sysctl.d/. Toujours tester avant production : certains paramètres peuvent casser des services (ex. rp_filter sur du routage asymétrique).

Démarrage

GRUB : mot de passe, permissions sur /boot/grub/grub.cfg, secure boot. Initramfs : protéger les secrets. Modules noyau : blacklister les modules inutiles (ex. squashfs, usb-storage) pour réduire la surface.

9

Journalisation, audit & patch management

Journalisation centralisée

Les logs doivent être déportés vers un serveur central, de préférence en temps réel, et protégés en intégrité.

Intérêts
  • Conservation des preuves si le serveur est compromis.
  • Détection et corrélation multi-serveurs.
  • L'attaquant ne peut pas effacer ses traces localement.
  • Conformité et audit.
Inconvénients
  • Charge réseau.
  • Point de défaillance unique (SPOF).
  • Latence possible.
  • Le serveur de logs doit être lui-même sécurisé.

Bonnes pratiques : NTP pour synchroniser les horodatages, TLS pour le transport, rotation/compression, rétention définie, accès restreint, alertes sur événements critiques, test de la chaîne de collecte. Outils : rsyslog, journald, auditd, SIEM (ELK, Splunk, Wazuh).

Patch management

Une mise à jour peut casser une application métier : incompatibilité, régression, arrêt de service. Dans une grande entreprise avec des applications critiques :

  1. Veille et inventaire des vulnérabilités.
  2. Environnement de test miroir (même OS, mêmes applications).
  3. Tests de non-régression et validation métier.
  4. Déploiement pilote sur un sous-ensemble.
  5. Déploiement progressif (rolling) avec fenêtre de maintenance.
  6. Snapshot/sauvegarde avant application, procédure de rollback.
  7. Haute disponibilité / cluster pour éviter l'arrêt.
  8. Vérification post-déploiement et documentaire.

Intégrité & malwares

AIDE/Tripwire : baseline des fichiers, détection de modification. Antivirus : signatures + comportement. EPP : antivirus + HIPS + firewall + gestion centralisée. EDR : détection, investigation, remédiation par comportement. XDR : EDR étendu au cloud et à l'hyperviseur. Rootkit : malware qui modifie le noyau ou les bibliothèques pour masquer sa présence.

Buffer overflow & protections mémoire

Un buffer overflow se produit quand un programme écrit plus de données que la taille allouée dans un tampon. Les données débordent sur les variables voisines, notamment l'adresse de retour sur la pile. L'attaquant peut alors détourner l'exécution vers son shellcode.

void f(char *input) {
  char buf[20];
  strcpy(buf, input);   // pas de contrôle de taille
}

Protections Linux

ProtectionRôleOption / commande
ASLRRandomise les adresses (pile, tas, libs).kernel.randomize_va_space=2
NX / DEPMarque la pile et le tas non exécutables.NX bit matériel.
Stack canaryValeur sentinelle avant l'adresse de retour ; détecte l'écrasement.-fstack-protector
PIEExécutable position-independent, compatible ASLR.-fPIE -pie
RELROProtège la GOT (table des symboles) en lecture seule.-Wl,-z,relro,-z,now
FORTIFY_SOURCEVérifie les fonctions dangereuses (strcpy, sprintf).-D_FORTIFY_SOURCE=2

Protections Windows

ProtectionRôle
DEPData Execution Prevention : zones de données non exécutables.
ASLRRandomisation des DLL, exécutables, pile et tas.
/GS (stack cookies)Canaries de pile du compilateur MSVC.
CFGControl Flow Guard : valide les appels indirects.

Réponse type

Sous Linux : ASLR, NX, canary, PIE, RELRO, FORTIFY, compilation sécurisée, revue de code, langages sûrs. Sous Windows : DEP, ASLR, /GS, CFG, SafeSEH/SEHOP, Device Guard. La protection est multicouche : une seule mesure ne suffit pas.

Windows est un noyau hybride. On distingue le mode utilisateur (applications, services, DLL) et le mode noyau (Executive, Kernel, HAL, pilotes, hyperviseur).

Windows : modèle de sécurité

Le token d'accès

À l'authentification, Windows construit un access token qui représente le contexte de sécurité : SID de l'utilisateur, SID des groupes, privilèges, niveau d'intégrité, session de logon. Chaque processus hérite d'un token.

Security descriptor, DACL, SACL

  • Propriétaire (SID).
  • DACL : liste des autorisations/refus (qui peut faire quoi).
  • SACL : liste d'audit (quels accès journaliser).
  • ACE : entrée individuelle de la DACL/SACL.

Le SRM compare le token de l'appelant au descripteur de sécurité de l'objet. Un refus explicite l'emporte généralement sur une autorisation.

SID

Identifiant de sécurité unique et immuable d'un compte, d'un groupe ou d'une machine. Il est utilisé dans les ACL et les tokens, pas « positionné sur une ressource ». SID bien connus : S-1-5-18 (SYSTEM), S-1-5-19 (LocalService), S-1-5-20 (NetworkService), S-1-5-32-544 (Administrateurs).

UAC & niveaux d'intégrité

UAC permet à un administrateur de travailler avec un token filtré (privilèges réduits) et d'élever ses droits uniquement quand c'est nécessaire. Une opération administrative déclenche une demande de consentement ; le programme élevé tourne avec un token complet. UAC applique le moindre privilège, il n'empêche pas un administrateur déterminé d'obtenir ses droits.

Niveau d'intégritéExemple
LowProcessus très restreint, sandbox (navigateur).
MediumApplication utilisateur standard.
HighProcessus élevé via UAC (administrateur).
SystemProcessus système critiques.

MIC (Mandatory Integrity Control) complète les ACL : un processus de niveau inférieur ne peut pas modifier un objet de niveau supérieur, même si la DACL l'autorise.

13

Windows : authentification & protections

Le chemin d'une ouverture de session

  1. Winlogon gère les sessions interactives : ouverture/fermeture, verrouillage, Ctrl+Alt+Suppr, lancement de l'environnement utilisateur.
  2. LogonUI affiche l'interface de connexion et collecte les identifiants via les credential providers.
  3. LSASS authentifie, applique la politique locale, crée le token et gère certains secrets.
  4. SAM contient les comptes locaux ; Active Directory gère les comptes de domaine.
Les 3 composants à ne pas confondre
  • Winlogon : sessions interactives, Ctrl+Alt+Del, lancement de l'environnement.
  • LSASS : authentification, politique, token, secrets.
  • SRM : contrôle d'accès aux objets, audit.

NTLM vs Kerberos

NTLMKerberos
TypeChallenge-response, hash NTLM.Tickets, KDC, TGT/TGS.
ContexteComptes locaux, workgroup, compatibilité.Active Directory.
AttaquesPass-the-Hash, relay NTLM.Pass-the-Ticket, Kerberoasting, Golden Ticket.

Credential dumping & LSASS

LSASS manipule en mémoire des hashs NTLM, tickets Kerberos et parfois des mots de passe. Un dump mémoire (Mimikatz, procdump, Task Manager) permet de les extraire et de les réutiliser (Pass-the-Hash, Pass-the-Ticket).

Pourquoi c'est critique

Un dump de LSASS peut compromettre l'identité sans connaître le mot de passe. Sur un contrôleur de domaine, il peut mener à la compromission totale du domaine.

Protections

  • LSA Protection / RunAsPPL : LSASS en processus protégé ; empêche le dump sauf driver signé.
  • Credential Guard : isolation des secrets via VBS (Virtualization-Based Security), donc l'hyperviseur.
  • TPM : protection matérielle des clés.
  • Désactiver WDigest : évite de stocker les mots de passe en clair en mémoire.
  • Windows Defender / EDR : détection des outils de dump.
  • Moindre privilège : limiter les comptes admin, utiliser des comptes dédiés et des postes d'administration (PAW).
  • Surveillance : alertes sur l'accès à LSASS, 4624/4672/4688.

Windows Hello

Authentification sans transmission du mot de passe : PIN, visage, empreinte. Le PIN sert localement à déverrouiller une clé cryptographique liée à l'appareil ; la clé privée ne quitte normalement pas le terminal. Réduit le phishing et le vol de mot de passe.

Si MPSSVC (firewall Windows) est vulnérable

Les mécanismes qui limitent les dégâts : isolation du service (SID restreint), ASLR, DEP, CFG, MIC/AppContainer, signature de code, moindre privilège, segmentation, EDR. Un service vulnérable ne doit pas automatiquement donner SYSTEM.

EAL4+ et C2

Common Criteria (ISO/IEC 15408) définit des niveaux d'assurance EAL1 à EAL7. EAL4+ correspond à une conception méthodique, des tests et une revue de sécurité ; c'est le niveau courant des OS grand public. C2 est une classe du TCSEC (norme américaine) : contrôle d'accès discrétionnaire, authentification, audit, protection mémoire.

Pourquoi difficiles à dépasser : complexité des OS (millions de lignes), coût et durée de certification, nécessité de preuves formelles (EAL7), incompatibilité avec certaines fonctionnalités grand public, accès au code source, évolutions permanentes.

Security by design

Intégrer la sécurité dès la conception, pas en rustine. Cela implique un cycle SDL : formation, exigences de sécurité, modélisation des menaces, revue de code, tests, réponse aux incidents. Microsoft l'applique depuis 2003 (Trustworthy Computing).

Questions ouvertes 2024

1 · Mise à jour d'un système avec applications métier critiques

Problème : incompatibilité, régression, arrêt de service. Processus : inventaire, veille, test miroir, non-régression, pilote, déploiement progressif, fenêtre de maintenance, snapshot/sauvegarde, rollback, haute disponibilité, communication. Principe : veille & maintenance + défense en profondeur.

2 · Journalisation centralisée temps réel

Intérêts : preuves conservées, détection rapide, corrélation, l'attaquant ne peut pas effacer localement. Inconvénients : charge réseau, SPOF, latence, sécurisation du serveur de logs. Bonnes pratiques : NTP, TLS, rotation, rétention, accès restreint, alertes.

3 · Set-UID root : risque, surfaces, bonnes pratiques, abandon ?

Voir section 5. Risque = escalade de privilèges. Surfaces = entrées, environnement, TOCTOU, shell, descripteurs. Bonnes pratiques = minimiser, auditer, nettoyer, abandonner les privilèges, capabilities. Abandon total impossible (passwd, sudo), mais réduction forte possible.

4 · Le point dans PATH

Si . est dans le PATH, le shell cherche d'abord dans le répertoire courant. Un attaquant place un faux ls ou sudo dans un répertoire où root travaille ; root l'exécute avec ses droits. Exemple : echo '#!/bin/bash' > /tmp/ls, puis root fait cd /tmp; ls. Solution : retirer . et les répertoires world-writable du PATH, utiliser des chemins absolus, ignore_dot dans sudo.

5 · Firewall Linux basé sur une ISO : démarche

Appliquer les principes : système minimal (pas de GUI, services essentiels), dépôts signés, partitioning, noexec/nosuid/nodev, SELinux/AppArmor, kernel sysctl, SSH par clés + 2FA, interface d'admin en HTTPS, firewall iptables/nftables deny all, logs centralisés, IDS/IPS, mises à jour signées, rollback, documentation, tests. Chaque choix doit être relié à un principe (minimisation, moindre privilège, défense en profondeur).

6 · Windows : Security by design, EAL4+/C2, Winlogon/LSASS/SRM

Voir sections 12 à 14. Security by design = sécurité dès la conception (SDL). EAL4+ = Common Criteria, C2 = TCSEC. Winlogon = sessions ; LSASS = authentification/token/secrets ; SRM = contrôle d'accès/audit.

7 · Vulnérabilité dans MPSSVC : qu'est-ce qui limite les dégâts ?

Isolation du service (SID restreint), ASLR, DEP, CFG, MIC/AppContainer, signature de code, moindre privilège, segmentation, EDR. Le service ne doit pas tourner avec des privilèges excessifs.

8 · LSASS memory dumping : danger et protection

Danger : extraction de hashs/tickets, Pass-the-Hash/Ticket, compromission du domaine. Protection : Credential Guard, LSA Protection/PPL, désactiver WDigest, Defender/EDR, moindre privilège, surveillance des accès, TPM.

9 · Niveau ANSSI « Renforcé » : situation, isolation, journalisation

Situation : serveur exposé à Internet, données sensibles, infrastructure critique. Isolation : namespaces, SELinux/AppArmor, chroot, conteneurs, VM. Journalisation : centralisation, intégrité, NTP, TLS, rétention, alertes, rotation, séparation des privilèges.

10 · Protéger contre le buffer overflow sous Linux et Windows

Linux : ASLR, NX/DEP, canary, PIE, RELRO, FORTIFY, compilation sécurisée. Windows : DEP, ASLR, /GS, CFG, SafeSEH/SEHOP, Device Guard. Les deux : validation des entrées, revue de code, langages sûrs, tests.
